# AI Agent 智能体

## AI Agent 概述

AI Agent 是一种能够自主感知环境、制定计划、调用工具并执行多步操作的智能系统。与传统 LLM 单次问答不同，Agent 会进行"观察 → 思考 → 行动 → 观察结果"的循环，直到任务完成。

**与直接调用 LLM API 做单次问答的本质区别**

- 单次问答：用户提问 → 模型一次性回答，无外部交互
- Agent：用户给出目标 → Agent 自主拆解任务 → 选择并调用工具 → 根据工具返回结果调整后续行动 → 循环直至完成，再将最终结果呈现给用户
- 核心差异在于闭环自主决策能力：Agent 不仅是"知道什么"，更是"能做些什么并在尝试中调整"
- Agent 系统的状态空间比单次问答大得多：每一次工具调用都可能改变后续决策路径

**Agent 的核心能力**

- 任务规划：将复杂目标拆解为可执行的子任务序列
- 工具使用：调用外部 API、数据库、代码执行器等扩展自身能力
- 记忆系统：维护短期上下文和长期知识
- 反思与纠错：根据执行结果调整后续策略

## ReAct 框架

ReAct（Reasoning + Acting）是 Agent 的核心推理-行动框架，将推理过程（Thought）和工具调用（Action）交替进行。

**ReAct 循环**

1. Thought（思考）：分析当前状态，决定下一步做什么
2. Action（行动）：调用工具或在环境中执行操作
3. Observation（观察）：接收工具返回结果或环境反馈
4. 回到步骤 1，直到输出 Final Answer

**为什么 ReAct 有效**

- 推理与行动交替形成"外部认知回路"：模型不需要一次性在脑中规划好所有步骤，可以在执行中逐步获得新信息并修正方向
- 观察结果注入上下文，纠正模型内部知识的偏差和幻觉
- 将复杂长链任务分解为多个短小步骤，每个步骤的上下文范围可控，降低模型在长程推理中的遗忘和漂移
- 用户或系统可以在每次 Observation 阶段介入审查和终止

**实现方式**

- 通过 prompt 模板引导模型按 Thought/Action/Observation 格式输出
- 在代码层解析模型输出 → 执行 action → 将结果重新注入 prompt
- 现代框架（LangChain Agent、AutoGPT 等）封装了此循环逻辑

## Function Calling / Tool Calling

Function Calling 是 LLM 调用外部工具的标准机制。模型不直接执行函数，而是输出结构化的调用意图。

**完整链路**

1. **工具定义**：开发者以 JSON Schema 描述每个工具的名称、描述、参数及类型约束
2. **请求提交**：将工具 Schema 列表与用户消息一并发送给 LLM
3. **LLM 决策**：模型判断是否需要调用工具，若需要则输出目标工具名称和参数 JSON
4. **代码执行**：开发者代码解析 LLM 输出，实际调用对应的函数
5. **结果回传**：将函数返回结果以 tool result 消息格式追加到对话上下文
6. **模型融合**：LLM 基于工具返回结果生成最终回答

**与 MCP 的关系**：Function Calling 定义了"LLM 如何表达调用意图"的契约，MCP 定义了"客户端如何发现和连接到工具服务"的契约。两者在不同抽象层，可以互补使用——MCP 负责工具的发现和传输，Function Calling 负责 LLM 侧的调用决策和参数生成。

**工具定义最佳实践**

- 描述清晰：名称见名知意，描述说明何时使用、功能边界
- 参数精简：只暴露真正需要的参数，避免冗余
- 枚举约束：对有限的选项使用 enum 类型限制
- 错误设计：工具返回结构化错误信息，帮助 LLM 修正后续调用

**工具 Schema 跨 Provider 差异处理**

不同 LLM Provider 对 Tool Schema 的支持不完全一致（参数类型、嵌套深度、required 字段语义等）。实践中通过适配层统一 Schema 定义，为每个 Provider 生成兼容格式。OpenClaw 在 Tool 层定义了标准 Schema，由 Provider Adapter 负责转换。

## Agent 记忆机制

Agent 的记忆分为三个层次，分别解决不同时间尺度的信息保持问题。

**短期记忆（Short-term Memory）**

当前对话轮次内的上下文，直接存在于模型的 context window 中。

- 存储方式：直接拼接在对话历史中
- 特点：容量受 context window 限制，对话结束即消失
- 挑战：长对话中信息溢出，需要在窗口满时做裁剪或压缩
- 典型容量：几十到几百轮对话，取决于每轮的长度

**长期记忆（Long-term Memory）**

跨会话持久化的信息，用于记住用户偏好、历史决策、频繁使用的知识和过往的交互片段。

- 存储方式：向量数据库（语义检索）+ 结构化存储（精确查询）
- 记忆写入：对话中自动提取关键信息（实体、偏好、决策）存入外部存储
- 记忆检索：新对话开始时，根据当前话题检索相关历史记忆注入 context
- 粒度设计：过细导致大量碎片化记忆难以管理，过粗导致检索到不相关内容干扰推理

**工作记忆（Working Memory）**

当前任务执行中的中间状态，如子任务进度、中间计算结果、已调用工具的历史。通常由 Agent 框架在内存中维护，不做持久化。

## Context Window 管理

Context Window 是 Agent 工程中最核心的约束之一——模型能同时"看到"的上下文有限。

**窗口超限的后果**

- 首部信息被截断（滑动窗口），丢失早期对话和初始指令
- 中间信息注意力稀释（Lost in the Middle 现象），模型对中间插入的文档片段关注度最低
- 推理质量下降，无法关联跨越窗口边界的上下文

**应对策略**

- **裁剪（Truncation）**：只保留最近 N 轮对话，丢弃更早的历史
- **摘要压缩（Summarization）**：对早期对话生成摘要保留关键信息，丢弃冗余细节
- **滑动窗口 + 固定预留**：最近的对话保持完整，早期对话做摘要，System Prompt 和工具定义始终占用固定空间
- **Compaction（OpenClaw 的核心概念）**：不仅仅是摘要，而是将对话中的关键信息重新组织为结构化上下文（决策记录、工具结果精华、关键发现），去掉已失效或不再相关的信息

**超大工具返回结果处理**

工具调用可能返回远超预期的数据（如代码搜索 50KB），直接塞入上下文会挤占宝贵窗口。

- 对返回结果做后处理截断，保留头部和关键行
- 让 LLM 针对返回结果生成摘要再注入上下文
- 分页返回，Agent 需要时再请求后续页
- OpenClaw 的做法：Context Engine 对工具返回结果做可控裁剪和结构化重组

## Agent 架构设计

### Single-Agent vs Multi-Agent

**Single-Agent（单智能体）**

一个 Agent 承担所有规划、推理、工具调用职责。

- 优点：架构简单，调试方便，上下文完整，无通信开销
- 缺点：单点能力上限，复杂任务时容易在长上下文中迷失方向
- 适用：任务边界清晰、工具集不大、不需要分工协作的场景

**Multi-Agent（多智能体）**

多个 Agent 各司其职，通过通信协议协作完成复杂任务。

- 优点：分工明确，每个 Agent 的上下文和工具体系独立，扩展性好
- 缺点：通信和协调开销，Agent 间的意图对齐和状态同步复杂

**Multi-Agent 组织模式**

- 层级式（Hierarchical）：主 Agent 拆解任务 → 分配给子 Agent → 汇总结果。类似技术主管分配任务给工程师
- 流水线式（Pipeline）：多个 Agent 依次处理，每个负责一个环节
- 辩论式（Debate）：多个 Agent 独立生成答案后相互评审和修正
- 群组式（Swarm）：动态选举或协商决策，无固定主从关系

**子 Agent（Subagent）的边界问题**

父 Agent spawn 子 Agent 时需要考虑：

- 上下文隔离：子 Agent 是独立实例还是共享父的上下文和工具？
- 权限控制：子 Agent 的工具权限应≤父 Agent，且在某些高风险工具上需要额外限制
- 超时与资源限制：子 Agent 的步数、时间、token 用量应有上限
- 错误传播：子 Agent 失败时，父 Agent 如何感知和处理
- OpenClaw 的做法：子 Agent 作为独立运行实例，通过 Gateway 进行规范的请求-响应通信，有独立的步数和时间限制

### Copilot 模式 vs Agent 模式

- **Copilot 模式**：人机协作，AI 辅助人类做决策。用户在循环中（Human-in-the-Loop），AI 提出建议，由人确认执行
- **Agent 模式**：AI 自主决策和执行。人类设定目标后，Agent 自行完成，人在循环外（Human-out-of-the-Loop），仅在关键节点或异常时介入

**两种模式的选择取决于**：任务风险等级、结果可逆性、用户信任度。实际系统中两者共存——低风险操作自动化（Agent 模式），高风险操作需要确认（Copilot 模式）。可通过工具策略管道（OpenClaw 的概念）对不同工具设置不同权限级别来灵活切换。

## OpenClaw 架构分析

OpenClaw 是一个插件化、多 Agent 可协作的开源 AI Agent 框架，解决生产级 Agent 系统的共性问题。

**核心组件**

- **Agent Runner**：负责一次 Agent 运行的完整生命周期——接收用户消息 → 加载上下文 → Agent 推理循环（ReAct）→ 输出最终结果
- **Gateway**：统一入口，管理多 Agent 的路由、会话、幂等性。所有消息通过 Gateway 分发到对应 Agent
- **Context Engine（可插拔）**：将上下文管理抽象为独立模块。支持不同策略：简单截断、摘要压缩、滑动窗口、结构化 Compaction 等
- **Channel Plugin（渠道插件）**：抽象消息来源的接入层。Telegram、飞书、钉钉各自实现 Channel 接口，上层 Agent 逻辑不变
- **Tool Plugin（工具插件）**：第三方可注册新工具。工具定义统一 Schema，Provider Adapter 负责适配不同 LLM
- **Hook System（中间件）**：Agent 生命周期的各个阶段（消息到达前、工具调用前/后、回答生成后）插入自定义逻辑

**一条消息的完整链路（OpenClaw）**

Channel（接收消息） → Gateway（路由匹配 → 幂等检查 → 会话管理） → Agent Runner（加载上下文 → 推理循环 → 工具调用） → Gateway（返回响应） → Channel（发送回复）

**Gateway 的幂等性设计**

Agent 系统特别需要幂等性，因为工具调用可能产生不可逆的外部副作用（发送消息、修改数据、扣款）。同一条消息如果因网络重试被重复处理，可能导致重复操作。Gateway 通过消息 ID 去重机制确保同一条消息只被处理一次。

**Hook 机制的应用场景**

- 敏感内容过滤：消息进入 Agent 前做安全扫描
- 审计日志：记录每次工具调用的参数和结果
- 使用计量：统计每次 Agent 运行的 token 消耗和工具调用次数
- 权限校验：工具调用前检查用户是否有权限

**会话隔离粒度**

同一用户在不同渠道上应如何管理会话？OpenClaw 的设计是：会话隔离粒度可配置——按用户 ID + 渠道组合隔离，或按用户 ID 全局共享。共享是更直接的体验，隔离避免跨渠道的信息泄露。具体选择取决于业务需求。

**多 Agent 间的通信**

Agent 之间通过 Gateway 进行通信——Agent A 发送一条"内部消息"给 Agent B，Gateway 做路由和状态管理，B 处理完毕后将结果返回给 A。Gateway 是 Agent 间通信的唯一中介。

## Agent 系统的高可用与性能

**LLM 服务高并发应对**

- 多 Provider 冗余：同时接入 OpenAI、Anthropic、Azure 等，一个 Provider 限流时自动切换
- 请求队列与限流：本地队列缓冲 + 按 token rate 做令牌桶限流
- 降级策略：高峰期使用更便宜/更快的模型处理低优先级请求
- 缓存：相同或高度相似的问题命中缓存直接返回（GPTCache）

**端到端延迟优化**

- 流式输出（Streaming）：边生成边返回，而非等全部生成完毕
- 工具调用并行化：独立的工具调用同时发起而非串行
- 更小的模型做简单决策：路由/过滤/分类等轻量任务用小模型
- 预热与连接池：LLM API 连接复用，减少握手开销
- 上下文长度控制：过长的上下文 = 更慢的首 token 生成速度（prefill 阶段开销与上下文长度成正比）

**Agent 服务稳健性保证**

- 超时机制：Agent 循环总超时 + 单步超时 + 工具调用超时，多层保护
- 重试策略：LLM API 瞬时错误做有限重试（exponential backoff）
- 熔断：连续失败时暂停服务，避免雪崩
- 兜底回答：所有路径失败时返回预先定义的友好回复
- 监控与告警：Agent 循环失败率、工具调用成功率、端到端延迟分布

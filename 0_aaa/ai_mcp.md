# MCP 与 A2A 协议

## MCP 协议（Model Context Protocol）

MCP 是由 Anthropic 提出的开放协议，定义了 AI 模型与外部工具、数据源之间的标准化通信方式。核心目标是为 LLM 提供一个"统一的外接接口"，让模型能够以标准化的方式发现和调用外部能力。

**MCP 解决的核心问题**

在 MCP 之前，每个 AI 应用都需要为自己的工具生态做定制集成——接入数据库需要单独写适配，接入文件系统又需要另一套。MCP 将这些集成抽象为标准的 Client-Server 协议，使工具提供方和 AI 应用方解耦。类比 USB 协议：MCP 是 AI 世界的"USB 接口"，MCP Server 是"USB 设备"。

**MCP 的核心组件**

- **MCP Host**：AI 应用本身（如 Claude Desktop、VS Code AI 插件），发起工具调用请求
- **MCP Client**：运行在 Host 内部的协议客户端，负责与各 Server 建立连接和通信
- **MCP Server**：轻量级服务，暴露特定的能力——数据库查询、文件操作、API 调用等。每个 Server 通过 standard input/output（stdio）或 HTTP 与 Client 通信

**MCP 支持的两种通信模式**

- **stdio 模式**：Client 以子进程方式启动 Server，通过标准输入/输出流做 JSON-RPC 通信。适合本地工具——Server 生命周期由 Client 管理，通信开销低，天然隔离
- **HTTP + SSE 模式**：Server 独立运行作为 HTTP 服务，Client 通过 Server-Sent Events（SSE）接收推送通知。适合远程服务——Server 可独立部署和扩展，多个 Client 可共享

**MCP 的工作流程**

1. **建立连接**：Client 启动 Server 或连接到远程 Server，建立通信通道
2. **能力协商**：Server 向 Client 声明自己提供的能力清单——工具列表（Tools）、资源模板（Resources）、提示模板（Prompts）。Client 将这些能力注册到 Host 的工具目录中
3. **工具发现**：LLM 需要调用工具时，Host 从已连接的所有 MCP Server 的工具列表中筛选匹配项
4. **工具调用**：Host 通过 Client 向目标 Server 发送 `tools/call` 请求，Server 执行实际逻辑后返回结果
5. **持续服务**：连接保持，Server 可持续提供服务直到 Client 主动断开

**MCP 协议安全性设计**

- 传输层：stdio 模式天然隔离在本地进程内；HTTP 模式建议使用 TLS 加密
- 认证层：HTTP 模式支持 Bearer Token 等标准认证机制
- 授权层：Client 在向 LLM 暴露工具之前进行前置校验，决定哪些工具对当前用户/会话可见
- 内容层：Server 返回的数据需要 Host 做二次校验，防止注入攻击
- 用户确认：高风险操作可要求用户显式确认后才实际执行

**MCP vs Function Calling**

| 维度 | MCP | Function Calling |
|------|-----|-----------------|
| 定位 | AI 应用与工具之间的通信协议 | LLM 表达工具调用意图的输出格式 |
| 解决的问题 | 工具的标准化发现、连接和调用 | LLM 如何结构化地表达"我要调哪个工具" |
| 抽象层 | 传输 + 发现 + 安全 | LLM 输出格式约定 |
| 标准化程度 | 跨模型、跨框架的开放协议 | 不同 Provider 的实现存在差异 |
| 关系 | MCP 负责"工具从哪来、怎么连" | Function Calling 负责"模型怎么表达调用意图" |

两者可以互补使用——MCP Server 提供工具，LLM 通过 Function Calling 决定调用哪一个，MCP Client 负责实际执行和返回结果。

**将已有应用转换为 MCP 服务**

在实践中，将现有应用或 API 包装为 MCP Server 的关键步骤：

1. 实现 MCP Server 协议的核心接口（`tools/list`、`tools/call` 等）
2. 将原有功能映射为工具描述（名称 + JSON Schema 参数定义 + 功能说明）
3. 处理参数转换：MCP 调用参数 → 原有接口参数
4. 处理结果转换：原有接口返回 → MCP 标准响应格式
5. Spring AI 等框架已提供现成的 MCP Server 基类和注解，降低集成成本

## MCP 与 Skills 的区别

**Skills**

Skills 是一种面向用户的、包含完整指令和工具逻辑的能力包。它不仅定义了"能做什么"，还包含了"怎么做"的 Prompt 模板和操作流程。

**MCP**

MCP 是底层工具协议，只关心"如何连接和调用外部能力"，不关心"如何使用这些能力来完成特定任务"。

**核心区别**

- MCP 提供的是原子化的工具（如查询数据库、读写文件）——粒度细，可组合
- Skills 提供的是特定任务的端到端解决方案（如"帮我写一份 PR 描述"）——粒度粗，直接面向用户目标
- Skills 内部使用 MCP 工具来完成操作——Skills 是上层应用，MCP 是底层设施
- MCP 解决"连接"问题，Skills 解决"任务编排"问题

两者是不同的抽象层：Skills 可以基于 MCP 工具构建，一个 Skill 在执行时可能会调用多个 MCP 工具。

## A2A 协议（Agent-to-Agent Protocol）

A2A 是由 Google 提出的多 Agent 之间通信和协作的开放协议，定义了 Agent 之间如何发现彼此、交换任务、协商能力和传递结果。

**五大设计原则**

1. **Agent 自主性**：每个 Agent 独立管理自己的内部状态、记忆和工具。A2A 只定义通信契约，不侵入 Agent 内部实现
2. **能力声明**：Agent 通过"Agent Card"声明自己的能力、支持的任务类型、输入输出格式和安全要求
3. **任务驱动**：通信以"任务"为基本单位——每个请求是一个结构化的任务对象，包含目标、约束、期望输出
4. **协作协商**：Agent 之间可以对任务范围、执行方式、结果格式进行双向协商，而非单方面指派
5. **安全与信任**：Agent 之间需要身份验证和授权，任务执行有沙箱约束

**A2A 的工作原理**

A2A 定义了标准的 Agent-to-Agent 通信模型：

1. **发现**：Agent A 通过 Agent Card 获取 Agent B 的能力描述——支持的任务类型、所需参数、认证要求、端点和协议版本
2. **任务提交**：A 构造结构化任务对象发送给 B，包含任务描述、输入数据、输出格式期望、优先级和截止时间
3. **执行与反馈**：B 执行任务并可选地发送中间进度通知（对于长时间任务），最终返回结果
4. **结果交付**：B 将结构化结果返回给 A，包含状态（成功/失败/部分完成）、输出数据、可选的错误信息

**工作流程**

A2A 的工作流程设计支持多种交互模式：

- 同步模式：A 提交任务 → 等待 B 完成 → 接收结果，适合短任务
- 异步模式：A 提交任务 → 获取 task ID → 后续轮询结果，适合长时间任务
- 流式模式：B 通过 SSE 持续推送中间结果和进度，适合需要实时反馈的场景

**A2A 与 MCP 的关系**

| 维度 | A2A | MCP |
|------|-----|-----|
| 通信对象 | Agent ↔ Agent | AI 应用 ↔ 工具/数据源 |
| 协议定位 | 多 Agent 协作 | 工具标准化接入 |
| 提出者 | Google | Anthropic |
| 通信粒度 | 任务级（高层次） | 工具调用级（原子操作） |
| 典型场景 | 多 Agent 分工完成复杂项目 | AI 应用调用数据库、文件系统等 |

两者解决不同层面的问题，可以在同一个系统中共存——Agent 通过 A2A 与其他 Agent 协作，同时通过 MCP 调用底层工具。两个协议在 Agent 架构中处于不同层级，不是替代关系。

**A2A 之外的多 Agent 通信方案**

- 共享消息总线（Message Bus）：所有 Agent 订阅同一消息队列，按主题发布和接收
- 中心化编排器（Orchestrator）：由编排 Agent 统一分配任务和协调结果
- 点对点直接调用：Agent 之间通过 API 直接调用（A2A 本质上是这种方案的标准化）

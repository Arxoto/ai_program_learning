# 提示工程与推理优化

## CoT 思维链（Chain of Thought）

CoT 是一种引导模型在给出最终答案前进行逐步推理的提示技术。

**原理**

在 prompt 中加入"让我们一步步思考"或提供分步推理的示例，引导模型将复杂问题拆解为中间推理步骤。模型在自回归生成每个后续 token 时，前面的推理步骤成为其自身的上下文，从而有条件地引导到正确的最终答案。

**为什么有效**

- 将隐式推理过程显式化为 token 序列，模型可以"看到"自己之前的推理来指导后续生成
- 将复杂问题分解为多个简单子问题逐步求解，降低了单步推理的难度
- 数学与逻辑推理任务中效果最显著——多步计算比一步到位更可靠
- 模型规模越大，CoT 效果越好（涌现能力的典型表现）

**缺点**

- 显著增加输出 token 数（推理步骤 + 最终答案），延迟和成本更高
- 推理链中早期步骤出错会传播到后续步骤（cascading errors）
- 过度自信：加了推理步骤后模型错误的倾向降低，但一旦错误更难发现（"看起来很有道理"）
- 简单任务不需要 CoT——强行要求逐步推理反而可能引入噪声
- CoT 的推理链不等于模型真正的推理过程，而是模型根据训练数据分布生成的"看起来像推理"的文本

**变体**

- Zero-shot CoT：只需添加"Let's think step by step"，无需示例
- Few-shot CoT：提供少量分步推理的示例
- Auto-CoT：自动生成推理链示例，减少人工编写
- Tree of Thoughts（ToT）：在每步推理时探索多个分支，而非一条线走到底
- Graph of Thoughts（GoT）：将推理过程建模为图，支持分支、合并、循环等更复杂的推理拓扑

## System Prompt 设计

在 Agent 系统中，System Prompt 承载了定义 Agent 行为边界的核心职责。

**核心职责**

- 角色定义：明确 Agent 的身份、能力范围和行为准则
- 行为约束：输出格式要求、禁止行为、安全边界
- 工具使用规范：何时及如何使用工具、工具结果的解读方式
- 上下文规则：如何处理对话历史、如何引用检索结果

**System Prompt 变长时的处理**

- 分层 System Prompt：核心指令放在最前面和最后面（模型的注意力在首尾最强），次要信息放在中间
- 动态 System Prompt：根据当前情境只注入相关的指令子集，而非全部
- 将参考性知识从 System Prompt 中移出，放到 RAG 检索或长期记忆中按需获取
- 定期精简和重构：排查已失效或冗余的指令，保持 System Prompt 精炼

## Prompt Caching

Prompt Caching 是一种通过缓存模型对前缀部分的内部计算来降低延迟和成本的优化技术。当多个请求共享相同的 prompt 前缀时（如相同的 System Prompt + 工具定义），前缀部分只需计算一次。

**工作原理**

- 缓存的是前缀的 Key-Value 注意力状态（K-V Cache），而非文本本身
- 后续请求若前缀匹配缓存，模型直接从缓存读取前缀的计算结果，跳过重复计算
- 匹配通常要求前缀完全一致（至少 token 级别），且对缓存的时间窗口有要求

**适用场景**

- 长而固定的 System Prompt（Agent 应用的典型场景）
- 批量处理时大量请求共享相同的前缀
- 长文档问答：文档内容作为前缀，被多个问题共享

## 护栏技术（Guardrails）

护栏技术是在大模型应用的输入和输出阶段设置的安全检查机制，防止有害内容进入或输出。

**输入护栏**

- 内容过滤：检测并拦截包含暴力、色情、仇恨言论等违规内容的请求
- 注入检测：识别 prompt injection（提示注入）攻击——用户试图通过特殊构造的输入覆盖 System Prompt 指令
- 敏感信息检测：识别用户输入中的 PII（个人身份信息）、密钥等
- 领域边界检测：拒绝超出 Agent 能力范围的请求

**输出护栏**

- 内容安全过滤：对模型输出做与输入相同的违规内容检测
- 事实性校验：关键事实声明与知识库做一致性比对
- 格式校验：验证结构化输出满足预期 Schema
- 合理化验证：对高风险操作（如删除数据、发送消息）的输出做二次确认

**实现方式**

- 基于规则：关键词列表、正则匹配——零延迟但易绕过
- 基于模型：用分类模型判断内容安全性——更智能但增加延迟和成本
- 两阶段结合：规则做快速初筛，模型做深度判断
- 可插拔设计：护栏作为独立模块注入到请求处理管道中

## GPTCache

GPTCache 是一个专门为 LLM 应用设计的语义缓存方案，通过缓存相似请求的 LLM 响应来降低延迟和 API 调用成本。

**核心思想**

传统的精确匹配缓存对 LLM 无效——用户的两个提问措辞不同但含义相同时，精确匹配无法命中。GPTCache 使用 Embedding 做语义相似度匹配，当新请求与缓存中的历史请求语义相似度超过阈值时返回缓存结果，而非重新调用 LLM。

**工作流程**

1. 请求到达 → 生成 Embedding
2. 在缓存中搜索语义相似的历史请求 → 若命中且相似度超阈值 → 返回缓存结果
3. 若未命中 → 调用 LLM → 将请求和结果存入缓存

**适用与不适用的场景**

- 适合：客服 FAQ、高频相似询问、系统提示重复的通用性问题
- 不适合：需要实时信息的查询、创造性任务、每次答案都应有差异的场景

## 大模型应用的趋势与方向

**Agent 化**：从"问答"到"执行"——模型不仅回答问题，更能自主使用工具完成复杂任务。Agent 将逐渐成为 AI 应用的主流形态。

**多模态融合**：文本、图像、音频、视频统一理解和生成，打破单模态限制。多模态 Agent 能同时处理截图、语音和文档。

**端侧推理**：模型量化和小型化，使大模型能在手机、PC 本地运行。隐私、低延迟场景的刚需。

**MCP/A2A 生态标准化**：工具接入和 Agent 通信协议的标准化，推动 AI 应用从垂直烟囱走向互操作的开放生态。

**长程自主执行**：Agent 能自主运行数小时甚至数天，完成需要多步规划、执行和验证的复杂项目（Manus 等产品验证了这个方向）。

**评估体系成熟化**：从定性感受走向定量指标 + 自动化回归，RAG 评估、Agent 评估的工具链会逐渐完善。

**成本与效率优化**：Prompt Caching、语义缓存、小模型路由、上下文压缩等技术持续降低生产部署成本。

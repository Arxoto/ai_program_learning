# RAG（Retrieval-Augmented Generation）

## RAG 概述

RAG（检索增强生成）是一种将信息检索与大模型生成能力相结合的技术架构，通过在生成回答前从外部知识库中检索相关信息，将检索结果作为上下文注入模型，从而提升回答的准确性、时效性和可溯源性。

**核心价值**

- 解决模型知识截止问题：注入最新信息，不依赖模型参数中的固化知识
- 降低幻觉：基于真实文档回答，减少模型凭空编造
- 可溯源：回答可关联到具体文档片段，便于验证
- 成本优势：无需重新训练模型即可更新知识，比微调更轻量

**RAG 完整流程（5 个核心阶段）**

1. **数据准备与预处理**：收集文档 → 清洗（去噪、去重、格式标准化） → 解析（从 PDF/HTML/Word 等提取纯文本 + 结构信息）
2. **索引构建（离线）**：文档分块 → 每个块生成 Embedding 向量 → 存入向量数据库
3. **查询阶段（在线）**：用户提问 → 查询处理（重写、扩展） → 生成查询 Embedding
4. **检索**：查询向量在向量库中做相似度搜索 → 召回 top-K 文档块
5. **增强生成**：将检索结果拼入 Prompt → 大模型基于上下文生成回答

在实际项目中，流程会多次往复——例如检索结果不理想时对查询做重写再检索，或生成回答后评估质量再进行补充检索。

**检索结果的增强方式**

- 作为上下文拼入 prompt（最常见）：在用户问题前插入检索到的文档内容
- 微调时的数据增强：用检索结果为微调样本补充上下文信息
- 检索结果与模型内部知识融合：部分高级架构允许模型在生成过程中动态参考检索结果

## 文档分块（Chunking）

**为什么需要分块**

- 模型上下文窗口有限，无法一次塞入完整文档
- 语义粒度匹配：过大的块包含噪声信息，降低检索精度；过小的块丢失上下文，割裂语义
- Embedding 模型有最大输入长度限制（通常 512 ~ 8192 token）

**常见分块策略**

- **固定长度分块（Fixed-size Chunking）**
  - 按固定 token/字符数切分，如每 512 token 一块
  - 优点：实现简单，计算开销最小
  - 缺点：可能在句中断开，破坏语义完整性
  - 通常配合 overlap（重叠窗口，如 10%~20%）来缓解边界割裂

- **基于分隔符分块（Recursive Character Splitting）**
  - 按段落 → 句子 → 词语的优先级递归切分，优先在高层次边界断开
  - LangChain 的 `RecursiveCharacterTextSplitter` 典型实现
  - 优点：尽量保持自然语言边界，语义完整性好
  - 适用大多数通用文档场景

- **语义分块（Semantic Chunking）**
  - 基于 Embedding 相似度判断断点：相邻句子间 Embedding 差异较大处自然断开
  - 优点：块与块之间的主题边界清晰
  - 缺点：需要额外 Embedding 计算，成本较高

- **句子级分块**
  - 以完整句子为最小单元，聚合至目标长度
  - 优点：语义完整，支持更多上层策略
  - 适用于 FAQ、对话记录等短文本场景

- **文档结构感知分块**
  - 利用 Markdown 标题层级、HTML 标签、PDF 书签等结构信息引导切分
  - 可保留章节/小节标题作为每个块的元数据，便于结构化检索
  - 优点：保留文档内在层级结构，检索时可利用标题元数据做过滤

- **特定场景分块策略**
  - 代码：按函数/类/文件切分，配合 AST 分析
  - 法律合同：按条款（Clause）切分
  - 长篇小说：按章节 + 语义段落双层切分，保留叙事连贯性

**分块粒度考量**

- 粗粒度（大块）：上下文丰富，但检索精度低，容易引入噪声
- 细粒度（小块）：检索精准，但碎片化可能丢失段落间的逻辑关系
- 实际项目通常采用混合粒度：小粒度块用于精准匹配，大粒度块（或父子块结构）提供完整上下文

**避免语义切割的实践**

- 固定 overlap：相邻块间保留 10% ~ 20% 的重叠文本
- 父子块递归：小块用于检索匹配，检索后合并或回溯到父块作为 LLM 上下文
- 句子边界对齐：使用句号、换行等自然分隔点，而不是硬截断
- metadata 标注：每个块标注来源文档、章节标题、页码等元数据，便于检索后重建上下文

## Embedding 在 RAG 中的角色

**原理**

将文本块和用户查询分别映射到同一向量空间，使得语义相关的文本在空间中距离相近。检索时通过向量相似度找到与查询最近的文档块。

**主流 Embedding 模型**

- OpenAI text-embedding-3-small/large：通用性强，多语言支持
- BGE 系列（BAAI）：bge-large-zh 中文表现优异，MTEB 基准排名靠前
- M3E：中文开源，轻量级，适合本地部署
- Jina Embeddings v2/v3：支持 8K token 长文本嵌入
- Cohere Embed：支持多语言和压缩向量（binary/quantized）

**选型考量因素**

- 目标语言的语义理解能力
- 最大输入长度是否匹配你的分块策略
- 向量维度（影响存储成本与检索速度）
- 是否支持自定义微调（领域适配）
- MTEB 基准表现作为参考，但必须在自己的数据上验证

## 向量数据库

**向量数据库原理**

向量数据库专门为高维向量数据的存储和相似度搜索优化，核心能力是 ANN（Approximate Nearest Neighbor，近似最近邻）搜索——在海量向量中快速找到与查询向量最相似的 k 个，而无需暴力比对。

**工作流程**

1. 向量写入：将 Embedding 向量和元数据（来源、文本内容等）写入数据库
2. 索引构建：对向量建立索引结构以加速搜索（通常在写入时触发或在后台异步构建）
3. 相似度搜索：输入查询向量，通过索引快速定位最近邻

**核心索引算法**

- **HNSW（Hierarchical Navigable Small World）**
  - 多层图结构，上层稀疏做长距离跳转，下层稠密做精细搜索
  - 查询速度快，召回率高，但内存占用大（需存储完整图结构）
  - 是当前多数向量数据库（Milvus、Weaviate、Qdrant）的默认算法
  - 适合对查询延迟敏感的场景

- **IVF（Inverted File Index）**
  - 先聚类将向量分配到不同桶（Voronoi 单元），查询时只搜索最近的若干个桶
  - 通过 PQ（Product Quantization，乘积量化）压缩向量以节省内存
  - 内存效率高，适合亿级以上大规模数据

- **LSH（Locality-Sensitive Hashing）**
  - 通过哈希函数将相似向量映射到同一个桶中
  - 理论简洁，但召回率通常不如 HNSW

**向量相似度度量**

- **余弦相似度（Cosine Similarity）**：衡量两个向量方向的一致性，值域 [-1, 1]，不受向量模长影响。最常用于文本 Embedding 检索，推荐对 Embedding 做归一化后使用
- **欧几里得距离（Euclidean Distance）**：衡量向量在多维空间中的直线距离，值域 [0, ∞)，受模长影响
- **曼哈顿距离（Manhattan Distance）**：衡量各维度绝对差之和，对异常维度不敏感
- **内积（Dot Product）**：归一化后等价于余弦相似度，部分数据库（如 Qdrant）推荐直接使用

一般使用归一化 Embedding + 内积/余弦相似度作为默认选择。

**主流向量数据库对比**

| 数据库 | 定位 | 特点 |
|--------|------|------|
| Milvus | 分布式大规模 | 存算分离，支持十亿级向量 |
| Qdrant | 高性能 | Rust 实现，过滤与向量搜索深度集成 |
| Weaviate | 全栈向量数据库 | 内置向量化、多模态支持 |
| Pinecone | 全托管云服务 | 零运维，按需付费 |
| Chroma | 轻量级 | 适合原型开发和本地测试 |
| FAISS | 算法库 | Meta 出品，纯算法库非数据库，性能极致但不带持久化/分布式 |
| pgvector | PostgreSQL 插件 | 与业务数据库一体，适合中小规模简单检索需求 |

**向量数据库选型考量**

- 数据量级（万级 → Chroma/pgvector；亿级 → Milvus 分布式）
- 查询性能要求（HNSW 参数调优空间）
- 是否需要混合过滤（标量过滤 + 向量搜索）
- 运维复杂度（自建 vs 云托管）
- 是否需要多模态（图片 + 文本混合检索）

## 检索优化

### 混合检索（Hybrid Search）

结合向量检索（语义匹配）与关键词检索（精确匹配，如 BM25）的优势，解决单一路径的短板。

- 向量检索擅长理解同义改写和语义相关性，但可能漏掉精确术语匹配
- 关键词检索擅长处理专有名词、缩写、代码标识符等精确匹配，但对同义表达束手无策
- 混合检索通过加权融合或 RRF（Reciprocal Rank Fusion）合并两路结果排序
- 实际项目中针对产品名称、型号、法律条文编号等需要精确匹配的字段保留 BM25 索引

### 多路召回

同时从多个异构数据源或使用多种检索策略获取候选集，再统一排序融合。

- 不同 Embedding 模型各自检索一路
- 向量检索 + 关键词检索 + 知识图谱检索各一路
- 不同粒度的块各自检索（小粒度块 + 大粒度上下文块）
- 多路结果通过 Rerank 模型统一排序

### 查询扩展（Query Expansion）

在检索前对原始查询做改写或扩展，增加检索覆盖范围。

- 用大模型生成相关子问题或多角度改写
- 用同义词表、领域术语库扩展关键词
- HyDE（Hypothetical Document Embedding）：先生成一份假设性答案，用该答案的 Embedding 去检索（比问题本身更接近文档的实际表达方式）

### 自查询（Self-Query）

让大模型从用户自然语言问题中提取结构化过滤条件（时间、作者、类别等），同时生成语义查询向量。将结构化过滤（metadata filter）与向量相似度搜索结合，适用于需要精确过滤 + 语义搜索的组合场景。

### Rerank（重排序）

第一阶段用向量检索快速召回候选集（如 top-100），第二阶段用更精确的 Rerank 模型对候选集精细排序（如精筛到 top-5）。

- Rerank 模型采用 Cross-Encoder 架构（而非向量检索的 Bi-Encoder），同时接收查询和文档对作为输入，计算两者的相关性分数
- 精度显著优于纯向量相似度排序，但计算开销大，不适合海量候选直接计算
- 主流方案：Cohere Rerank、bge-reranker、Jina Reranker
- 实践中，Rerank 是性价比最高的检索精度提升手段之一

## Advanced RAG 与 Modular RAG

**Naive RAG**：单次检索 → 单次生成，简单但效果有限。

**Advanced RAG**

在 Naive RAG 基础上引入检索前和检索后的优化策略：

- 检索前：查询重写、查询扩展、自查询
- 检索中：混合检索、多路召回
- 检索后：Rerank、提示压缩、结果去重与融合
- 生成：上下文选择与排序、引用标注

**Modular RAG**

将 RAG 的各个组件模块化，使其可以根据实际需求自由组合、替换和迭代：

- 检索模块：支持多种检索器（向量、关键词、图谱）的即插即用
- 记忆模块：利用对话历史优化查询意图理解
- 路由模块：根据不同问题类型自动选择最优检索策略
- 任务适配模块：下游任务（问答、摘要、代码生成）使用不同的检索和提示策略

模块化使得 RAG 系统更灵活可演化，允许每个模块独立更新或替换。

## 提示压缩（Prompt Compression）

解决检索结果过多导致上下文超限和注意力稀释问题。

**核心思想**：在保证关键信息不丢失的前提下，压缩检索结果和对话历史的长度。

**常见方法**

- 大模型摘要压缩：让 LLM 对长文本进行摘要再放入 prompt
- 选择性过滤：对每个检索块计算与查询的相关性分数，低于阈值的丢弃
- Token 级压缩（如 LLMLingua）：用小模型或启发式方法删除冗余 token 和句子
- 滑动窗口：只保留最近 N 轮对话历史的核心信息
- 结构化压缩：保留关键实体和关系，丢弃修辞性内容

提示压缩与 RAG 系统的上下文管理是同一问题的两个维度，通常配合使用。

## 数据清洗与预处理

**文档解析**

- PDF：区分扫描件（OCR）和文本型（直接提取），处理多栏布局和表格
- HTML：去除导航、广告、脚本等噪声，保留正文结构
- 表格与图表：保留结构化表示，转化为文本描述或独立的 tabular 索引
- 多模态文档：图文分离，保留图文对应关系元数据

**数据清洗**

- 去重：文档级去重 + 段落级重复检测
- 格式标准化：统一换行符、空白字符、特殊字符
- 语言检测：过滤不需要的语言内容
- 低质量内容过滤：过短文档、纯数字/符号、无意义重复内容

**元数据管理**

- 来源标注：文档名称、路径、更新时间、页码/行号
- 结构标注：标题层级、所属章节
- 权限标注：访问控制和数据敏感性标记

## RAG 效果评估

**检索质量评估**

- 召回率（Recall）：相关文档中有多少被检索出来
- 精确率（Precision）：检索出来的文档中有多少是相关的
- MRR（Mean Reciprocal Rank）：第一个相关文档的平均排名倒数
- NDCG（Normalized Discounted Cumulative Gain）：考虑排序位置加权的相关性评估
- Hit Rate：top-K 中至少有一个相关文档的问题比例

**生成质量评估**

- 忠实度（Faithfulness）：回答是否完全基于检索到的上下文，是否存在过度推断或编造
- 答案相关性（Answer Relevance）：回答是否直接回应了问题
- 上下文相关性（Context Relevance）：检索结果是否与问题相关
- 端到端评估（End-to-End）：用户视角的整体满意度

**实际评估落地**

- 构建标注数据集（至少数百条问答对，覆盖典型场景和边缘 case）
- 标注"理想答案"和"理想检索结果"两套标准
- 使用评估框架：RAGAS、TruLens、LangSmith 等
- 大模型辅助评估（LLM-as-Judge）：用更强的模型对答案质量打分，降低人工成本
- 定期回归测试，作为 CI/CD 的一部分防止退化

## RAG vs 微调

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 实时，更新文档即可 | 需重新训练 |
| 成本 | 检索基础设施 + API 调用 | GPU 训练资源 |
| 可解释性 | 高，可溯源文档 | 低，知识隐式编码在参数中 |
| 事实准确性 | 依赖外部知识库质量 | 依赖训练数据质量和覆盖范围 |
| 领域特化深度 | 通用，靠检索补充 | 深度适配领域风格和术语 |
| 延迟 | 检索增加额外延迟 | 无额外延迟 |

**选择策略**：先 RAG 后微调。RAG 能解决 80% 的知识注入需求，只有当需要模型固化特定风格、术语或推理模式时才考虑微调。两者不是互斥的——RAHF（RAG + Fine-tuning Hybrid）在实际中最常见。

## 大模型幻觉（Hallucination）

**幻觉类型**

- 事实性幻觉：编造不存在的事实、数据、引用
- 忠实性幻觉：回答偏离给定的上下文或指令约束
- 逻辑性幻觉：推理链条存在逻辑断裂或矛盾

**缓解策略**

- 强 RAG 体系：检索真实文档作为回答依据
- 提示约束：在 system prompt 中明确要求"不知道就说不知道"
- 引用强制：要求模型在回答中标注信息来源
- 评估反馈循环：用评估指标和用户反馈持续优化
- 低温度 + 结构化输出：降低模型自由发挥空间
- 护栏技术：在输出阶段进行规则或模型校验

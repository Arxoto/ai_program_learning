# Spring DB

## Spring 事务隔离

使用 `@Transactional` 注解的方法，其内部的所有 SQL 共享同一个数据库事务，异常自动回滚。
本质是封装 JDBC 连接级别设置，由数据库提供隔离性，但提供了抽象层与具体数据库解耦。

级别与对应 JDBC 中的隔离级别
- ISOLATION_DEFAULT 使用数据库默认隔离级别
- ISOLATION_READ_UNCOMMITTED 读未提交
- ISOLATION_READ_COMMITTED 读已提交
- ISOLATION_REPEATABLE_READ 可重复读
- ISOLATION_SERIALIZABLE 可串行化

事务隔离级别
- 读未提交
  - 一个事务可以读取另一个未提交事务的修改
  - 允许脏读、不可重复读、幻读
- 读已提交
  - 一个事务只能读取其他事务已经提交的数据
  - 防止脏读，但存在不可重复读、幻读
- 可重复读
  - 事务内多次读取同一行数据，结果保持一致，不受其他事务提交的影响（ MVCC 生成的一致性视图）
  - 防止脏读、不可重复读，但可能存在幻读
- 可串行化
  - 事务完全串行执行
  - 防止脏读、不可重复读、幻读

名词解释
- 脏读：读到其他事务可能回退的数据
- 不可重复读：同一事务内两次相同的查询，如果中间有其他事务提交了修改，第二次会看到不同的结果
- 禁止不可重复读：事务开始时建立一致性快照（MVCC）或持有行锁，保证同一查询结果不变
- 幻读：同一事务内两次相同的查询，如果中间有其他事务提交了插入，第二次会看到多的数据

在 **可重复读** 级别下，若基于 SELECT 的结果去 UPDATE 更新数据，可能使其他事务的更新丢失。解决方案如下：
- 悲观锁：对该行施加 **排他锁** ，直至事务提交或回滚， `SELECT ... FOR UPDATE`
- 乐观锁：添加 version 字段，更新时增加 version 条件来保证版本一致，失败需要重试
- 原子更新：适用于简单运算场景， `UPDATE xx SET x = x - 1`
- 升级隔离级别至 SERIALIZABLE 可串行化

DB 锁介绍
- 共享锁，允许多个事务持有，并发读、写阻塞 `SELECT ... LOCK IN SHARE MODE` / `SELECT ... FOR SHARE`
- 排他锁，只允许一个事务持有， UPDATE/DELETE 自动加锁， SELECT 手动加锁 `SELECT ... FOR UPDATE`
- 悲观锁/乐观锁 是应用层的设计思想，不是实际存在的锁
- 记录锁/间隙锁/临键锁 是锁力度，由引擎根据语句通过算法决策的

MySQL InnoDB 的行锁算法（锁粒度）
- 记录锁 Record Lock ，锁住单个索引记录，阻止其他事务修改/删除该记录
- 间隙锁 Gap Lock ，锁住索引记录之间的间隙，阻止向间隙中插入新记录，在可重复读级别下极大程度避免了幻读（不加锁的快照读不保证）
- 临键锁 Next-Key Lock ，即 记录锁+间隙锁

## Spring 事务传播行为

事务传播行为定义了一个事务方法被另一个事务方法调用时， **是否以及如何复用当前事务** 。
- 允许将单一服务的原子性行为组合和更大颗粒的原子单元
- 允许某些操作独立提交或脱离事务，不入侵业务代码

具体传播行为
- REQUIRED
  - 必须在事务中（默认）
  - 若已存在事务：加入当前事务
  - 若不存在事务：新建事务
- REQUIRES_NEW
  - 必须新建独立事务
  - 若已存在事务：挂起当前事务，新建独立事务
  - 若不存在事务：新建事务
- SUPPORTS
  - 支持在事务中（也可不在）
  - 若已存在事务：加入当前事务
  - 若不存在事务：以非事务方式执行
- NOT_SUPPORTED
  - 不支持在事务中（独立执行）
  - 若已存在事务：挂起当前事务，以非事务方式执行
  - 若不存在事务：以非事务方式执行
- MANDATORY
  - 强制在事务中（否则报错）
  - 若已存在事务：加入当前事务
  - 若不存在事务：抛出异常
- NEVER
  - 从不在事务中（否则报错）
  - 若已存在事务：抛出异常
  - 若不存在事务：以非事务方式执行
- NESTED
  - 嵌套事务
  - 若已存在事务：创建嵌套事务（保存点机制）
  - 若不存在事务：新建事务

## 事务失效的情况

- 未启用事务管理
- AOP 代理机制导致
  - 类内部调用自身方法
  - 非 public 方法
  - final 类或 final 方法
- 数据库或存储引擎不支持
- 异常被处理没有抛出
- 抛出了受检异常（仅 `RuntimeException` 或 `Error` 触发回滚）
- 传播行为配置不当，中断了事务的传播
- 多线程环境

## SQL 优化

**索引优化**

- 覆盖索引避免回表：查询的列全部包含在索引中，无需再访问数据行
- 高频条件建立索引， `WHERE` / `JOIN` / `ORDER BY` / `GROUP BY`
- 最左前缀原则：联合索引 `(a, b, c)` 相当于创建了 `(a)` / `(a,b)` / `(a,b,c)` 三个索引，查询条件也必须按照这个顺序，否则导致索引失效
- 避免索引失效：不在索引列上使用函数或运算、避免隐式类型转换、 `LIKE` 以 `%` 开头无法使用索引
- 区分度决定索引价值：区分度极低的列（如性别）不宜单独建索引。

**SQL 语句优化**

- 按需取列：只 SELECT 需要的列，而不是 `SELECT *`
- 小表驱动大表：JOIN 时，让数据量小的表（过滤后的结果集、非原始表大小）作为驱动表，并确保被驱动表的连接字段必须有索引
  - 合理选择 IN 与 EXISTS ：外层表大而子查询表小用 IN （先执行子查询得到结果集、此时子查询相当于驱动表），外层表小而子查询表大用 EXISTS （外层表带入执行子查询、外层表相当于驱动表）
- 优化大偏移量分页： `LIMIT 1000000,10` 可改为基于游标的分页 `WHERE id > last_id LIMIT 10`
- 索引下推 ICP ，传统方式在找到一条符合索引条件的记录后立即进行回表，在 Server 层判断其他 WHERE 条件是否满足；有索引下推后，在存储引擎层就直接过滤，防止回表（主要针对二级索引的场景，因为聚簇索引本身叶子节点就是实际数据，不会回表）
- 拆分 OR 条件：对非索引列的多个 OR ，可改写为 UNION 走多个索引查询

## 慢 SQL

- 需要开启慢查询日志，默认阈值 10s
- 使用 `EXPLAIN` 查看语句的执行计划，关注是否走索引、扫描行数（全表扫描）、临时表、文件排序（非索引排序会走内存排序、内容过大会 filesort 用到临时文件做归并排序）等

## 主键类型

- 单机，自增主键，性能最佳
- 分布式，雪花算法，“时间戳+机器ID+序列号”
- 【不要】 UUID ，无需会导致索引性能问题

## 缓存穿透

- 缓存空对象（遇到空查询也缓存），但无法抵御攻击
- 前置布隆过滤器（存储可能存在的键），低概率把不存在判定为存在，此时请求会达到数据库，但是概率很低
- 网关限流，令牌桶（允许突发，处理峰值）或漏桶算法（强制平滑，削峰填谷）
